# TauriTavern Web Docker

This project packages the TauriTavern 2.3.0 frontend with a browser host and a private Rust application service. It is intended for one user on a trusted home network.

## Start

1. Copy `.env.example` to `.env` and set `TT_WEB_PASSWORD` to a unique password with at least 12 characters.
2. Run `docker compose up --build -d` from this directory.
3. Open `http://<NAS-address>:8080` and sign in with that password. Set `TT_WEB_PORT` in `.env` to change the published gateway port.

Compose publishes only the gateway port. The Rust service has no host port mapping and is reachable only on the private Compose network. The named `tauritavern-data` volume stores chats, characters, settings, secrets, world info, and related application data. `docker compose down` keeps that volume. Back it up before replacing the deployment; deleting the volume deletes the data.

Set the password before starting the gateway. Login sessions are signed, HTTP-only, SameSite cookies and expire after eight hours. The gateway limits failed login attempts. Use HTTPS in front of the gateway before accessing it over an untrusted network. The app asks before connecting to an unrecognized custom model endpoint because API keys, prompts, and chat content may be sent to that endpoint.

## Architecture

- `gateway`: serves the built frontend, login page, and authenticated API, event, and channel proxies. It is the only service with a published host port.
- `app`: Rust host for the browser adaptation layer and TauriTavern application services. It has no published host port.
- `.github/workflows/web-container-build.yml`: builds both images for `linux/amd64` and `linux/arm64` without publishing them.

## Current browser support

The browser host implements bootstrap, settings and settings snapshots, secrets, model connections and provider metadata, character and group data (including duplicate/rename/replace and lorebook conflict management), chat persistence/search/recent summaries/backups, cold-chat reads and windowed history, per-chat extension storage, presets, world info, avatars/personas, user media, assets, backgrounds and folders, sprites, themes, quick replies, MCP server/tool management, Agent Skill import/edit/export/scope management, extension discovery/install/update/delete/version/branch management, extension JSON/binary storage, Agent profiles/runtime/persistent-state management, tokenizer operations, TTS, and vector routes. Browser uploads use authenticated same-origin staging, and staged paths are accepted only from the application-owned upload directory. Third-party extension manifests, JavaScript modules, stylesheets, and other files are served from the local extension directories and loaded in the app page. Agent live tool and reasoning updates use an authenticated browser WebSocket channel. User presets, extension data, MCP registrations/catalogs, Skills, and Agent workspaces are stored in the persistent data volume; built-in defaults are copied into the app image. Character card JSON/PNG, world info, and full application archive import/export use browser file transfers. Archive uploads stream to disk with a 1 GiB limit. Chat file reads and uploads use authenticated same-origin routes. The integration test exercises an OpenAI-compatible mock stream, extension discovery and executable module serving, extension JSON/binary storage, user media and file management, character and group chat administration, MCP and Skill management, Agent profile/tool APIs, archive ZIP export and download, and persistence after a host restart.

Third-party extension JavaScript and CSS run in the app page, but extensions that call desktop-only Tauri plugins or unsupported host commands may not work. Developer diagnostic panels support frontend logs, web-host invoke errors, and model request/response logs; model logs persist in the data volume using the configured retention count. Diagnostic bundles download through the browser and include frontend, backend, and model logs. Model request/response content can include prompts and chat text, so review a bundle before sharing it. API keys and sensitive fields are redacted from recorded request data. Backend diagnostics cover web-host invoke failures rather than the full Rust tracing stream, and Tauri backend event listeners beyond the Agent live channel are not implemented. LAN Sync, TT-Sync, and sync automation still depend on desktop services and are not implemented in this browser host. Local-folder reveal actions and iOS share/picker APIs are not applicable to this browser target. Browser notifications use the browser Notification API and require a secure context. Full command and UI compatibility still needs an explicit audit; this list is not a claim of complete parity.

## Validation status

Frontend production build, TypeScript, guardrails, startup/navigation, gateway, contract, browser-host integration, UI, Rust workspace tests, and Clippy were run locally. Contract tests passed 482/491, with nine Linux installer tests skipped because POSIX `sh` is unavailable on this Windows host. All 166 UI tests passed. Rust workspace tests passed with the symlink-copy test filtered because Windows denied symlink creation (error 1314); Clippy passed. The x86-64 Compose build, unauthenticated API rejection, login, gateway-only host port, extension JSON/binary storage, and persistence-after-restart checks pass locally. The ARM64 app image cross-compiles on the build host; the ARM64 gateway image builds its frontend on the build platform and packages the ARM64 Node runtime. Both run under emulation. ARM64 Compose login, unauthenticated API rejection, gateway-only host port, app and gateway health, and persistence-after-restart checks also pass. The gateway health check allows 10 seconds for startup so it remains reliable on slower ARM systems. The gateway's tests run in the build-platform stage because they start Node child processes. The DH4300 Plus has not been tested yet, so verify startup, login, model streaming, and persistence on that NAS before publishing images.
